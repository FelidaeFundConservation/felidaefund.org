# Homepage, built for Joomla

The prototype front page, packaged so it can go live on felidaefund.org on
its own — without migrating the rest of the site. Joomla's header, footer
and menus are untouched.

Generated by `tools/build-joomla-homepage.py`. Edit the prototype, re-run
the script, don't hand-edit these three files.

| File | Goes where |
|---|---|
| `article.html` | the homepage **article**, in code view |
| `homepage.css` | appended to `templates/genesis4/css/digi-custom.css` |
| `homepage.js`  | uploaded next to it, loaded by the template |

`../prototype/joomla-preview.html` shows the result with the live site's
four real stylesheets **and its real header and footer**, so it can be
reviewed before anything is pasted. The chrome is saved in
`tools/joomla-header.html` and `tools/joomla-footer.html`; re-save them
from felidaefund.org if the live menu changes.

## Steps

1. **Copy the current homepage article's HTML somewhere safe first.** It is
   a single article. If this goes wrong mid-fundraising-season you want the
   old one back in one paste, not reconstructed.
2. Upload the 19 images (3.8 MB, listed below) to Joomla media at
   `/images/homepage/`, keeping the `badges/` subfolder.
3. Append `homepage.css` to `digi-custom.css`.
3b. **Add the missing font weights**, or the page will not match the
   preview. The template self-hosts Raleway at 400 and 800 only, and
   Literata at 300 and 800 only. The homepage asks for Raleway 500, 600
   and 700 and Literata 400, none of which exist, so the browser
   substitutes the nearest: headings and buttons render 800 (too heavy)
   and body text renders 300 (too light). Add this to the template's
   `<head>`, above `digi-custom.css`:

   ```html
   <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
   <link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Literata:wght@400&family=Raleway:wght@500;600;700&display=swap">
   ```

   It requests only the four missing weights, so the weights the rest of
   the site already uses keep coming from the local files and nothing
   else changes.
4. Upload `homepage.js` and load it from the template, or put it in a
   Custom HTML module with text filtering off. Don't paste it into the
   article: a later edit in the WYSIWYG editor will mangle it.
5. Make a **new** article, paste `article.html` into it in **code view**,
   and add a menu item pointing at it with **Access = Special**. That is
   the staging URL — only logged-in staff can see it.
6. When it's approved, edit the Home menu item to point at the new article.
   Rollback is that same field.

Set the editor to CodeMirror or None in your user profile before step 5.
TinyMCE rewrites hand-written HTML when you toggle between visual and code
view, and it will quietly break the layout.

## What was changed from the prototype, and why

- **Donate buttons** now point at `#XSZEWCKT`, the Fundraise Up anchor the
  live site already uses sitewide. The prototype's donation modal is a
  mockup — its submit button has no handler — so it is dropped entirely.
  Fundraise Up's script is already in the template `<head>`; nothing to add.
- **All 17 internal links** rewritten from prototype filenames to live URLs.
  Every one was checked and returns 200. `projects.html` became
  `/projects/research`, because the live site has no `/projects` index.
- **Images** repointed to `/images/homepage/`.
- **`.mission` and `.news` renamed** to `.fx-mission` and `.fx-news`. Those
  were the only two class names that collided with the live homepage's own
  CSS, and renaming beats an `!important` fight.
- **Every section carries `full-width`**, the template's own escape hatch.
  Without it the template boxes sections to 1170px.
- **All CSS is scoped under `.fx-home`**, including the element-level resets
  on `html`, `body`, `img`, `a` and `button`, which would otherwise leak
  into Joomla's header and footer. `html` is dropped; `body` becomes
  `.fx-home`.
- **The parked theme picker** and its `[data-theme="2"]` rules are left out.

## Checked against the live site

- Collisions: all 96 prototype classes tested against `special-pages.css`,
  `template.css`, `digi-custom.css` and the JCE editor's `content.min.css`.
  Only `.mission` and `.news` hit, both handled above.
- Two template rules reach the new markup, both neutralised in a single
  labelled block at the top of `homepage.css`:
  - `.home section + section { margin-top: … !important }`
  - `* + :not(:first-child):not(main):not(.igui-lightbox) { margin-top: 24px }`
    — the template's global flow spacing. It puts 24px on top of *every*
    element that has a preceding sibling, which the prototype's `margin:0`
    reset does not expect. It was pushing the hero's Donate button 24px
    below Read His Story (and stretching Read His Story to match), and
    pushing the Donate panel 24px below the Volunteer panel. The six
    margins the design does want are restored at the end of the file.

  A class-name collision check does not catch this one — it is a universal
  selector. Anything pasted into this site needs checking for it.
- Design tokens: no name clash with any of the live site's 144 CSS variables.
- Rendered under the live cascade at 1440px and 375px: no horizontal
  overflow, every section full-bleed, all 19 images load, counters animate,
  scroll reveals fire.
- **Hero height.** The prototype's nav floats over the hero, so the hero is
  `100dvh`. Joomla's header is sticky and sits above the article instead,
  taking 172px on desktop and 94px on mobile. Left alone the hero ran past
  the fold and took its own Donate button with it. The hero is now
  `calc(100dvh - var(--fx-hero-offset))`, measured at runtime by
  `homepage.js`. Verified: hero bottom lands exactly on the fold at both
  1440x900 and 375x812, with both buttons above it.

## Where Joomla can still differ from the preview

The preview loads the live stylesheets, header and footer, so layout and
colour are trustworthy. These are the things it cannot show:

- **Fonts.** Handled by step 3b above. The preview loads the full weight
  range from Google, so it flatters Joomla until that link is added.
- **The editor.** TinyMCE rewrites hand-written HTML. Use code view with
  the editor set to None or CodeMirror.
- **Content plugins.** Joomla plugins transform article HTML at render
  time, and some wrap images or inject markup. Nothing in the live
  homepage suggests this happens, but it only shows up once pasted.
- **Template JavaScript.** The preview does not run it, so the mobile
  menu and any scroll behaviour on the header are untested here.
- **Image paths.** The preview reads from `prototype/assets`; Joomla will
  read from `/images/homepage/`. Joomla's media manager can also resize
  on upload.

The way to close the gap is step 5: paste into an unpublished article
behind an `Access = Special` menu item, then open that URL and the
preview side by side at the same window width. Anything that differs is
one of the five above.
